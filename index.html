معماری کامل سیستم

همه‌چیز از یه نقطه شروع می‌شه (main.py) و از لایه‌های ثابتی رد می‌شه — قبل از اینکه هیچ هانتری اجرا بشه.

جریان کامل یک اجرا

  1. Overseer.seed_recon() برای هر دامنه‌ی scope یه تسک recon می‌سازه
  2. ReconHunter اجرا می‌شه: subfinder → فیلتر scope → httpx → فیلتر scope → katana → فیلتر scope
  3. از روی نتیجه، seed_vuln_hunters_from_recon() به‌صورت قطعی (نه حدس LLM) و بعد از فیلتر DiffScan، همه‌ی هانترهای دیگه رو seed می‌کنه
  4. یه دور تکمیلی، plan_next_steps() از Gemini می‌پرسه چیز اضافه‌ای هم لازمه یا نه — با همون ScopeGuard دوباره فیلتر می‌شه
  5. هر هانتر روی صف خودش اجرا می‌شه؛ هر finding با report_finding() ثبت می‌شه
  6. برای هر finding یه گزارش draft مارک‌داون توی reports/ ساخته می‌شه
  7. core/scan_runner.py کل این جریان رو توی یه تابع واحد پیچیده — هم CLI هم داشبورد همینو صدا می‌زنن

۰۴

تنظیم فایل‌های Config

این بخش رو با دقت انجام بده — این‌ها لایه‌ی محافظتی واقعی سیستمن.

اجباری

۴.۱ — scope.json

terminal
cp config/scope.example.json config/scope.json

با scope رسمی برنامه پرش کن:

{ "program_name": "نام-برنامه", "in_scope": ["target.com", "*.target.com"], "out_of_scope": ["blog.target.com"] }
نکته‌ی مهم درباره‌ی out_of_scope
برخلاف in_scope (که برای شامل کردن زیردامنه‌ها باید صریحاً از *. استفاده کنی)، هر آیتم توی out_of_scope به‌صورت پیش‌فرض همه‌ی زیردامنه‌هاشو هم رد می‌کنه، حتی بدون *.. یعنی "internal.target.com" هم خودش هم api.internal.target.com رو رد می‌کنه. این عمداً این‌طوریه: برای یه ابزار امنیتی، رد کردن بیش‌ازحد بی‌خطره، ولی از قلم انداختن یه چیزی که باید رد بشه می‌تونه یعنی اسکن یه چیزی که مجاز نبوده.
اختیاری

۴.۲ — settings.json

پیش‌فرض‌ها معقولن. اگه policy برنامه سقف نرخ درخواست اعلام کرده، همینجا تنظیمش کن.

{ "requests_per_second": 5 }

رعایت‌نکردن این محدودیت می‌تونه باعث بن‌شدن اکانتت بشه.

اختیاری

۴.۳ — auth.json

فقط برای IDORHunter — باید session اکانت تست خودت باشه، نه شخص دیگه.

{ "session_a": { "cookie": "PHPSESSID=...", "headers": {"Authorization": ""} }, "session_b": {"cookie": "", "headers": {}} }
  • فقط session_a پر باشه: چک می‌کنه داده‌ی نیازمند لاگین بدون auth هم در دسترسه (broken access control)
  • هر دو پر باشن: تست دقیق‌تر IDOR (آیا اکانت B به منبع اکانت A دسترسی داره)
  • بدون این فایل: تست increment/decrement بدون session انجام نمی‌شه و IDORHunter عملاً skip می‌شه

هر ۱۱ هانتر

هر هانتر یه فایل جدا توی hunters/ هست. اکثرشون روی همون لیست URL‌های crawl‌شده اجرا می‌شن — بدون seeding جداگانه.

زیرساخت مشترک
IDOR، XSS، CORS/Redirect، و SSRF دقیقاً همون لیست param_urls (هر URL دارای query parameter) رو به اشتراک می‌ذارن. یعنی اگه یکی روی یه URL تست می‌کنه، بقیه هم همون‌جا و با همون diff-filtering اجرا می‌شن.
🛰️

ReconHunter

هانتر پایه — نقطه‌ی شروع هر اسکن

سه ابزار رو زنجیره می‌کنه: subfinder (پیدا کردن ساب‌دامین) → فیلتر ScopeGuard → httpx (چک زنده‌بودن) → فیلتر دوباره → katana (کراول URL) → فیلتر دوباره. خروجی نهایی (ساب‌دامین‌ها، هاست‌های زنده، URLها) پایه‌ی seed شدن همه‌ی هانترهای دیگه‌ست.

چرا فیلتر سه بار؟
هر مرحله جدا از ScopeGuard رد می‌شه — نه فقط خروجی نهایی. یعنی حتی اگه subfinder یه زیردامنه‌ی خارج از scope برگردونه، همون‌جا حذف می‌شه و هیچ‌وقت به httpx/katana نمی‌رسه.
🔓

IDORHunter

Broken Access Control + Cross-Account IDOR

۳ نوع تست، بسته به اینکه auth.json رو چقدر پر کرده باشی:

تستنیاز به config
Broken Access Control (بدون auth، داده در دسترسه؟)session_a
Cross-Account IDOR (اکانت B به منبع A دسترسی داره؟)session_a + session_b
Sequential ID Access (نیاز به بررسی دستی)بدون session هم اجرا می‌شه

بدون auth.json پرشده، فقط تست سوم اجرا می‌شه — برای IDOR واقعی، حتماً بخش ۴.۳ رو پر کن.

⚡

XSSHunter

Reflected XSS + تأیید واقعی با مرورگر

payload رو توی هر پارامتر تزریق می‌کنه، بعد اگه Playwright نصب باشه، واقعاً توی یه Chromium headless صفحه رو باز می‌کنه و چک می‌کنه alert() واقعاً اجرا شد یا نه.

حالتconfidence
Playwright نصب و alert() واقعاً اجرا شدconfirmed
Playwright نصب نیست، فقط reflection دیده شدcandidate
🌐

CorsRedirectHunter

CORS Misconfiguration + Open Redirect

تست CORS — سه نوع Origin ساختگی

نوع تستچی می‌فرستهیعنی چی اگه reflect بشه
arbitrary_origin_reflectedدامنه‌ی کاملاً بی‌ربطسرور هیچ allowlistی نداره
null_origin_trustedOrigin: nullقابل exploit از iframe sandboxed
prefix_match_bypasshttps://{هدف}.{ساختگی}باگ کلاسیک: چک "شروع می‌شه با" نه "برابره با"

severity: اگه Access-Control-Allow-Credentials: true باشه → critical، وگرنه medium.

تست Open Redirect

مقدار هر پارامتر رو با یه دامنه‌ی نشانه‌دار (marker تصادفی و یکتا) عوض می‌کنه — ۳ نوع payload (URL کامل، // protocol-relative، بک‌اسلش) — و چک می‌کنه سرور ۳xx با Location اشاره‌کننده به همون marker می‌ده یا نه.

🎯

SSRFHunter

Server-Side Request Forgery

روش ۱ — تشخیص غیر-blind (بدون سرویس خارجی)

مقدار پارامتر رو با http://169.254.169.254/latest/meta-data/ (متادیتای AWS/GCP/Azure) یا http://127.0.0.1/ عوض می‌کنه و چک می‌کنه پاسخ امضای متادیتا داره (مثل instance-id, ami-id). اگه پیدا بشه: critical + confirmed (قطعیه، نه حدس).

روش ۲ — OOB Callback اختیاری

برای SSRF کور (fetch می‌شه ولی reflect نمی‌شه)، نیاز به یه سرویس Out-of-Band مثل interactsh:

  1. یه دامنه‌ی OOB بگیر
  2. از داشبورد → «⚙️ تنظیمات» → فیلد «SSRF — دامنه‌ی OOB»
  3. دور بعدی اسکن، یه ساب‌دامین یکتا (توکن تصادفی) تزریق می‌شه
  4. باید خودت دستی بری داشبورد OOB رو چک کنی — ابزار نمی‌تونه callback رو خودش تأیید کنه
📡

NucleiHunter

اسکن با تمپلیت‌های عمومی community

روی هر هاست زنده، nuclei رو با تمپلیت‌های عمومی community اجرا می‌کنه — CVEهای شناخته‌شده و misconfigurationهای رایج. برخلاف Template Forge (بعدی)، تمپلیت‌ها از پیش نوشته شدن، نه مخصوص این هدف خاص.

🔨

TemplateForgeHunter

تولید تمپلیت Nuclei سفارشی با AI

از روی سیگنال‌های واقعی همین هدف خاص (هدر Server، محتوای صفحه)، با کمک Gemini یه تمپلیت YAML مخصوص همین اپ می‌سازه — چیزی که هیچ تمپلیت عمومی‌ای پوشش نمی‌ده.

تنها هانتری که HTTP probe رو خود AI می‌سازه — لایه‌ی validation اجباری
هر تمپلیت قبل از هر استفاده‌ای باید: YAML معتبر با ساختار nuclei کامل باشه، از متد DELETE/PUT/PATCH استفاده نکنه، شامل کلیدواژه‌ی خطرناک (DROP TABLE, rm -rf) نباشه، و فیلد id فقط حروف/عدد/-/_ باشه (این آخری بعد از ممیزی امنیتی اضافه شد — بخش ۱۱). اگه رد نشه: نه ذخیره می‌شه نه گزارش می‌شه.

پیش‌فرض template_forge_auto_execute: false — تمپلیت فقط validate و روی دیسک (generated_templates/) ذخیره می‌شه، اجرا نمی‌شه. باید دستی از داشبورد فعالش کنی تا با nuclei روی هدف اجرا بشه.

🔍

ParamMinerHunter

کشف پارامتر مخفی (سبک arjun)

هانترهای پارامتر-محور فقط پارامترهایی رو می‌بینن که katana توی کراول پیدا کرده. خیلی از اپ‌ها پارامتر مخفی دارن (debug=true, admin=1) که هیچ‌جا لینک نشدن. این هانتر یه لیست منتخب ۶۱ اسم رو تک‌تک تست می‌کنه.

۶
baseline متفاوت برای تخمین نویز صفحه
۶۱
اسم پارامتر پرکاربرد تست می‌شه
۲۵/۲۵
کشف موفق در calibration، <۰.۲٪ false positive
⚡️ ارزش واقعی: زنجیره‌ی خودکار
وقتی یه پارامتر مخفی پیدا بشه، خودش یه finding اطلاعاتی (severity: info) ثبت می‌شه، ولی مهم‌تر: همون لحظه URL جدید برای IDOR، XSS، CORS/Redirect، و SSRF هم صف می‌شه. سطح حمله‌ای که سایر هانترها می‌بینن، بزرگ‌تر از چیزیه که فقط از کراول معمولی به دست میومد.
👻

TakeoverHunter

Subdomain Takeover

برای هر ساب‌دامین، CNAME رو resolve می‌کنه. اگه به یه سرویس شناخته‌شده اشاره کنه (GitHub Pages، Heroku، S3، Shopify، Netlify و ۱۰ سرویس دیگه — config/takeover_fingerprints.json)، یه HTTP request می‌فرسته و بدنه رو با امضای "claim نشده" مقایسه می‌کنه.

severity بالاست (high/critical) چون یعنی هر کسی می‌تونه اون سرویس رو با اسم خودش ثبت کنه و کنترل کامل ساب‌دامین معتبر رو بگیره (فیشینگ، دزدی کوکی، XSS).

قبل از گزارش، حتماً این کار رو بکن
تنها راه تأیید ۱۰۰٪ اینه که واقعاً همون سرویس رو با اکانت خودت ثبت کنی و ببینی ساب‌دامین هدف به محتوای توئه اشاره می‌کنه یا نه — بهترین Proof of Concept برای گزارشه. با احتیاط و طبق قوانین برنامه انجامش بده.

fingerprintها گاهی قدیمی می‌شن — هر چند وقت با can-i-take-over-xyz سینک کن.

🔑

SecretsHunter

افشای کلید API / توکن

روی همه‌ی URLهای کراول‌شده (خصوصاً .js, .json, .map, .env) با ۱۴ الگوی regex دنبال کلید می‌گرده: AWS، Google، Stripe، GitHub، Slack، Twilio، SendGrid، Firebase، JWT، و یه الگوی عمومی با فیلتر entropy. همچنین چک می‌کنه فایل‌های .js به source map اشاره می‌کنن یا نه.

این ابزار عمداً هیچ کلید پیداشده‌ای رو تست نمی‌کنه
فقط پیدا می‌کنه و با masking (AKIA****...MPLE) ذخیره می‌کنه. چون تست فعال یه کلید روی سرویس شخص ثالث می‌تونه از scope خارج بشه یا قوانین اون سرویس رو بشکنه. توی گزارش صادقانه بنویس «پیدا کردم، تست نکردم».
📊

DiffScan

اسکن افتراقی / Incremental — یه seeding mechanism، نه یه vuln hunter

قبل از اینکه هر asset به idor/xss/secrets/nuclei/takeover فرستاده بشه، از core/diff_store.py رد می‌شه: «این asset رو قبلاً برای همین برنامه دیده بودیم؟» — فقط چیزهای واقعاً جدید صف می‌شن.

توی bug bounty معمولاً نفر اول که گزارش می‌ده پول می‌گیره. DiffScan باعث می‌شه هر اسکن مستقیم بره سراغ چیزهایی که همین امروز تازه ظاهر شدن.

محدودیت مهم
فقط "URL/دامنه‌ی جدید" رو تشخیص می‌ده، نه "محتوای تغییرکرده". اگه یه فایل JS قبلاً چک شده ولی محتواش عوض شده، دوباره چک نمی‌شه. برای این مورد، هر چند وقت (مثلاً هفتگی) از داشبورد بخش هانترها، «بازنشانی تاریخچه» رو بزن.
📚

آموزش هانترها (Knowledge Base)

یه فیچر داشبورد، نه یکی از ۱۱ هانتر

می‌تونی رایتاپ‌های منتشرشده، تکنیک‌های تازه، یا یادداشت خودت رو تگ‌شده به یه هانتر خاص (یا «عمومی») ذخیره کنی.

صادقانه بگم چیکار می‌کنه و چیکار نمی‌کنه
این پایگاه‌دانش منطق قطعی/regex-based هانترها رو خودکار تغییر نمی‌ده. SecretsHunter همیشه همون ۱۴ الگو رو چک می‌کنه. چیزی که واقعاً استفاده می‌کنه، بخش planning Overseer هست: وقتی از Gemini می‌پرسه «قدم بعدی چیه؟»، یادداشت‌های تو هم به‌عنوان context اضافه می‌شن.

۲ راه استفاده:

  • خودکار: فقط با اضافه‌کردن یادداشت، خودش توی planning استفاده می‌شه
  • دستی («🔍 پیشنهاد الگو»): از Gemini می‌خواد از متن یادداشت الگوی قابل‌اتوماسیون استخراج کنه — نتیجه فقط پیشنهاده، هیچ فایل کدی خودکار تغییر نمی‌کنه

حتی اگه یه یادداشت باعث بشه Overseer یه هدف عجیب پیشنهاد بده، همون ScopeGuard دوباره چکش می‌کنه قبل از صف‌شدن.

۰۸

داشبورد وب — مرکز فرماندهی

دیگه فقط read-only نیست — از اینجا می‌تونی کل سیستم رو مدیریت کنی، بدون دستکاری دستی فایل‌های JSON.

terminal
cd dashboard
python app.py

مرورگر رو باز کن: http://127.0.0.1:5000

⚠ هشدار امنیتی مهم
این داشبورد الان write-access کامل به سیستم داره (می‌تونه اسکن اجرا کنه، scope رو عوض کنه، API keyهاتو ببینه/عوض کنه). همیشه فقط روی 127.0.0.1 نگهش دار. هیچ‌وقت:
  • host="0.0.0.0" نکن
  • پورت ۵۰۰۰ رو forward نکن
  • از ngrok / cloudflare tunnel برای expose کردنش استفاده نکن
هر کسی که به این پورت دسترسی پیدا کنه، عملاً کنترل کامل ابزار امنیتی‌ت و کلیدهات رو به دست میاره.
محافظت CSRF (از این نسخه)
این داشبورد login/session نداره (عمداً — ابزار لوکال تک‌کاربره‌ست)، برای همین هر بار app.py اجرا می‌شه یه توکن تصادفی تازه ساخته می‌شه. یعنی اگه چند تا تب داشبورد از قبل از یه ری‌استارت باز مونده، بعد از ری‌استارت باید همه‌شونو رفرش کنی — وگرنه با خطای «CSRF token نامعتبر» (۴۰۳) مواجه می‌شن. نیازی به کار دستی دیگه‌ای نیست.

بررسی و ارسال گزارش‌ها

فایل‌های reports/*.md شامل Summary، Steps to Reproduce (خودت پرش کن)، Evidence خام، Impact، Suggested Fix، و یه چک‌لیست بالای فایل.

قبل از ارسال هر گزارش

  1. خودت دستی، با مرورگر یا Burp/curl، آسیب‌پذیری رو reproduce کن
  2. مطمئن شو داده‌ی واقعی کاربر دیگه‌ای رو بیش از حد لازم نخوندی

  5. فقط بعد از این مراحل ارسال کن
یادت باشه
همه‌ی findingها پیش‌فرض candidate هستن — یعنی اسکنر حدس زده، نه قطعی ثابت کرده. استثنا: XSSHunter با Playwright، CorsRedirectHunter، و SSRFHunter در حالت metadata-reflected — این‌ها confirmed می‌زنن. حتی اون‌هام بهتره دستی چک کنی. یافته‌ی OOB-candidate توی SSRF همیشه candidate می‌مونه چون بدون چک دستی داشبورد OOB قابل تأیید نیست.

ممیزی امنیتی نهایی و باگ‌های فیکس‌شده

نتیجه‌ی یه ممیزی کامل روی خود ابزار (نه هدف‌های اسکن‌شده): هر ۱۱ هانتر روی یه اپ لوکال ساختگی (هم نسخه‌ی آسیب‌پذیر هم امن هر endpoint) اجرا شد، کل داشبورد از طریق API واقعی تست شد، و در مجموع ۹ باگ واقعی پیدا و فیکس شد.

دور اول ممیزی

#۱

باگ سازگاری API در ParamMinerHunter و TakeoverHunter

نتیجه‌ی execute() توی این دو هانتر با الگوی بقیه یکی نبود (کلید findings جا افتاده یا مفرد به‌جای لیست). کد فعلی داشبورد/scan_runner از این مستقیماً اثر نمی‌گرفت، ولی هر کد دیگه‌ای که انتظار ساختار یکسان داشته باشه می‌تونست بشکنه.

✅ فیکس شد — هر ۱۱ هانتر دقیقاً همون قرارداد رو رعایت می‌کنن
#۲

Path Traversal در report_generator.py

شدت: متوسط

اسم فایل گزارش از vuln_type ساخته می‌شد با جایگزینی فقط space و : — یعنی / و .. دست‌نخورده می‌موندن. چون vuln_type برای TemplateForgeHunter شامل فیلد title هست که خودِ Gemini بر اساس سیگنال‌های هدف اسکن‌شده می‌سازه، یه هدف خصمانه از نظر تئوری می‌تونست با یه تلاش prompt injection باعث بشه گزارش خارج از پوشه‌ی reports/ نوشته بشه.

✔ اثبات شد با PoC محلی (فایل واقعاً بیرون نوشته شد)  ·  ✔ فیکس شد با whitelist سخت‌گیرانه + چک دوم قبل از نوشتن  ·  ✔ ۱۰ vuln_type واقعی دوباره تست شد، بدون regression
#۳

Path Traversal در template_forge_hunter.py

شدت: متوسط تا بالا

فیلد id توی YAML تولیدشده توسط Gemini فقط از نظر «وجود داشتن» چک می‌شد، نه محتوا — یه id: ../../../x می‌تونست فایل رو خارج از generated_templates/ بنویسه (مستقیم‌تر از #۲، چون کل YAML رو می‌نویسه نه فقط اسم فایل).

✔ اثبات شد با PoC محلی  ·  ✔ فیکس شد با regex امن (^[A-Za-z0-9_-]+$) داخل validate_template() — الان id نامعتبر همون‌جا رد می‌شه
#۴

CSRF روی تمام endpoint های POST داشبورد

شدت: بحرانی

داشبورد auth/session نداره، و چون request.get_json(force=True) صرف‌نظر از Content-Type بدنه رو JSON پارس می‌کنه، یه صفحه‌ی مخرب می‌تونست با یه درخواست ساده (بدون CORS preflight) به /api/scope/domain/add بزنه و دامنه‌ی دلخواه خودش رو به in_scope اضافه کنه، بعد /api/scan/start رو صدا بزنه — یعنی ابزار امنیتی خودت رو بی‌اطلاع خودت علیه هدفی که هیچ برنامه‌ای مجازش نکرده مسلح کنه.

✔ اثبات شد با شبیه‌سازی دقیق حمله  ·  ✔ فیکس شد با توکن تصادفی per-process (بخش ۰۸)  ·  ✔ دوباره تست شد — حمله‌ی شبیه‌سازی‌شده الان ۴۰۳ می‌گیره
#۵

Stored XSS توی داشبورد

شدت: بحرانی، قابل زنجیره‌شدن با #۴

مقادیر finding (vuln_type، target)، دامنه‌ها، اسم برنامه‌ها، و یادداشت‌های Knowledge Base مستقیم و بدون escape توی innerHTML رندر می‌شدن. مسیر واقعی نگران‌کننده: همون فیلد title که Gemini برای TemplateForgeHunter می‌سازه، بدون sanitize مستقیم وارد جدول findingها می‌شد. زنجیره‌ی خطرناک: یه CSRF کور می‌تونست مقدار مخرب توی scope تزریق کنه که وقتی خودت داشبورد رو باز می‌کنی اجرا بشه — و چون داشبورد کلید Gemini و session کوکی‌هاتم مدیریت می‌کنه، تأثیرش تا افشای اون‌ها هم می‌رسید.

✔ اثبات و بازتأیید شد با Chromium واقعی (Playwright) — دو finding خصمانه تزریق شد، هیچ alert()/onerrorای اجرا نشد  ·  ✔ فیکس: escapeHtml() روی تمام دیتای سرور، صرف‌نظر از «قابل‌اعتماد» بودن
#۶

Path Traversal در /api/programs/load

شدت: پایین تا متوسط

برخلاف /api/programs/save که اسم برنامه رو sanitize می‌کنه، نسخه‌ی load این کار رو نمی‌کرد — یه اسم مثل ../../../etc/x می‌تونست فایل JSON دلخواه رو بخونه و روی scope.json کپی کنه.

✅ فیکس شد با همون sanitize نسخه‌ی save — تلاش path-traversal الان ۴۰۴ برمی‌گردونه
نکته‌ی مهم درباره‌ی مسیر Overseer
بخش ۶.۱۰ از قبل تست کرده بود که ScopeGuard جلوی پیشنهاد خارج از scope رو از plan_next_steps می‌گیره — این هنوز درسته. چیزی که این ممیزی اضافه کرد یه لایه‌ی مکمله: حتی وقتی هاست پیشنهادی داخل scope باشه، اگه رشته‌ی target شامل کاراکترهای عجیب باشه، فیکس #۵ (escape در داشبورد) مستقل از منبع اون رشته محافظت می‌کنه.
محدودیت این دور تست
subfinder/httpx/katana/nuclei (نیازمند Go) و پکیج google-genai روی محیط تست من قابل‌نصب نبودن (بدون دسترسی شبکه). برای Recon/Nuclei مسیر «graceful degradation وقتی ابزار نصب نیست» و منطق پارس/فیلتر severity (با subprocess شبیه‌سازی‌شده) تست شد، ولی اجرای واقعی خود این ۴ باینری روی یه هدف واقعی نه. توصیه: این‌ها رو نصب کن و main.py رو یه بار روی یه scope کوچیک اجرا کن — این ممیزی جایگزین اون یه‌بار اجرای دستی نیست، مکملشه.

دور دوم ممیزی (پس از درخواست بازبینی مجدد)

جدای از تکرار تست‌های بالا، ۳ باگ واقعی دیگه پیدا کرد — دوتاش این بار روی عملکرد بودن، نه فقط امنیت.

#۷

باگ بحرانی (functional): دکمه‌ی «شروع اسکن» توی داشبورد همیشه شکست می‌خورد

بحرانی

core/scan_runner.py از مسیرهای نسبی استفاده می‌کرد ("config/scope.json", "tasks.db"، به‌علاوه‌ی دیفالت‌های diff_db_path/knowledge_db_path توی Overseer.__init__). این مسیرها از main.py (CWD = ریشه‌ی پروژه) درست کار می‌کردن، ولی وقتی دقیقاً طبق همین راهنما از داشبورد اجرا می‌شدن (cd dashboard && python app.py، یعنی CWD = dashboard/)، دنبال dashboard/config/scope.json می‌گشتن که وجود نداره — یعنی دکمه‌ی «شروع اسکن» بلافاصله با خطا شکست می‌خورد، و حتی اگه رد می‌شد، دیتابیس‌ها جدا و اشتباه زیر dashboard/ ساخته می‌شدن؛ یعنی حتی اگه اسکن جایی موفق می‌شد، نتیجه‌هاش هیچ‌وقت توی خود داشبورد دیده نمی‌شدن.

✔ با اجرای دقیق همون سناریوی مستندشده‌ی همین راهنما اثبات شد (دکمه رو دقیقاً همون‌طور که مستنده زدم و خطا رو گرفتم)  ·  ✔ فیکس شد با الگوی PROJECT_ROOT مطلق  ·  ✔ تأیید شد: «شروع اسکن» از داشبورد الان end-to-end کار می‌کنه

به همین دلیل، دیفالت داخلی FindingsStore هم برای یکدستی و ایمنی در برابر همین اشتباه در آینده، مطلق شد.
